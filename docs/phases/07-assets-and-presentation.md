# Phase 7: Assets and presentation

**Status: done** (signed off 2026-11-18). Size: 2 to 4 sessions. Depends on: phase 2. Can run alongside other phases, one part at a time.

## Goal

Raise how the game looks and sounds: imported models where they help, better lighting and effects, proper audio, and gamepad support.

## Why now

Not before phase 2, because frame silhouettes and hardpoints should be settled before models are made or chosen for them. After that it can proceed whenever art is available.

## Decide first

1. Art direction. Stay stylised low-poly, or aim for more detail?
2. Where assets come from: CC0 packs, the user's own models, or keep procedural and improve it.
3. Audio source: better synthesis, CC0 samples, or original recordings. Music or not.
4. Performance budget on the user's machine, from the phase 1 baseline.

## Decisions (settled 2026-11-17)

1. **Art direction: more detailed.** Move away from flat boxes: bevelled and panelled parts, PBR
   materials with surface detail (panel lines, wear, roughness), better lighting. Detail is
   spent where it shows (mechs, effects) and every addition has a quality setting.
2. **Assets: procedural, plus the glTF pipeline.** Improve the procedural parts, and build the
   full glTF path (`GltfPartVisual`, manifest, fallback, attribution file). It is proven with
   models generated by a script in this repo; models from elsewhere can be dropped in later
   without code changes.
3. **Audio: better synthesis, no music.** Rework the WebAudio sounds and make them positional.
   No audio files.
4. **Budget: 60 fps** in a five-mech fight on the 2019 16-inch MacBook Pro (phase 1 baseline:
   3.5 ms JS, 1.9 ms GPU per frame). Shadows, particles and post-processing each get a quality
   setting; the default must hold the budget.

## Build steps

1. **`GltfPartVisual`.** A second implementation of `PartVisual` in `src/view/parts/` that loads a glTF model, exposes named attachment points, and maps pose channels to bones or authored clips. Gameplay code does not change.
2. **Asset pipeline.** A folder for models, a manifest mapping part ids to files, loading with a procedural fallback while a model loads or if it is missing, and an attribution file listing source and licence for every asset.
3. **Swap parts one at a time.** Start with one frame's torso to prove the path, then continue as assets arrive. Procedural and imported parts can coexist on one mech.
4. **Animation.** Authored clips where available, procedural otherwise; blend between walk, run, jets and recoil.
5. **Cockpit interior.** A modelled cockpit replacing the flat overlay, with instruments driven by the same state the HUD reads.
6. **Lighting and effects.** Shadows, particle effects for jets, impacts and explosions, restrained post-processing. Each addition measured against the budget, with quality settings to turn it down.
7. **Audio.** Replace or improve the synthesised sounds in `src/view/audio.ts`; positional audio; music if wanted.
8. **Gamepad.** Second input source in `src/game/input.ts` producing the same `Intent`.
9. **HUD polish.** Readability pass, consistent with the chosen art direction.

## What is built so far

- Steps 1 to 3. `GltfPartVisual` (`src/view/parts/GltfPartVisual.ts`) draws a part from a glb
  with the procedural part kept underneath as its rig and as the stand-in while loading or if
  the file is missing. Model nodes named `joint.<name>` follow the procedural joint of that name
  (so the procedural animation moves them), `att.<name>` nodes replace attachment points, and
  materials named primary, secondary, accent, metal and dark take the faction's colours. The
  manifest is `src/data/models.ts`; files are in `public/models/` with `ATTRIBUTION.md` beside
  them (a unit test checks every file is listed and credited). Every part of all three frames
  and the four weapon shapes now has a detailed model, generated by `npm run models`
  (`scripts/make-models.mjs`, a small glb writer with no dependencies). `?procedural` in the URL
  draws the old procedural parts, for comparison.
- Performance after the first playtest traces (2026-11-17). Models doubled the draw calls of a
  fight (Medium: 584 against 304 procedural), costing 4 to 7 ms of game JavaScript a frame on
  the reference machine, and a squad waking caused 60 to 67 ms frames. Fixes: a model is now
  turned into a prototype per faction (`src/view/parts/modelPrototypes.ts`) whose pieces are
  merged per node into painted, bare-metal and accent meshes, with the faction's colours in the
  vertices and two palette materials shared by every faction; mechs copy the prototype. All
  prototypes are built and their materials compiled behind the start screen. The second trace
  showed draw calls fixed but game JavaScript unchanged: the cost was per mesh, not per draw
  (Babylon walks every listed mesh each frame, and each mech copied 86 meshes, kept its hidden
  procedural ones, and 110 disabled prototypes sat in the scene). So mechs now get instances of
  the prototype's merged meshes and plain nodes for the rest, the procedural meshes are
  disposed once a model is in, and prototypes are taken out of the scene's lists. The next
  traces (2026-11-18, Medium) showed the CPU fixed (scene render 6.4 ms in a fight against 5.1
  procedural) but GPU time up from about 4 ms to 7 to 11 ms, one fight dropping to 38 fps.
  Headless render timing pinned it on the instances (about 20% more GPU-side work than plain
  copies), so mechs now get plain mesh copies built by hand (Mesh.clone was most of the wake
  cost). Headless, models against procedural: building a mech 14 ms against 10 (was 59),
  per-frame mesh walk with ten mechs 0.35 ms against 0.26 (was 2.71), software render of a
  fight 12 ms against 9 (instances: 19). Traces now record the quality preset, whether models
  were on, and live particles. To be re-measured on the reference machine.
- Step 4. Authored clips named `pose.<channel>` are scrubbed by that pose channel (the
  backpack's vent flaps open with thrust); other clips play once through `playClip`. Walk,
  stride, airborne, brace and recoil stay procedural and blend continuously as before.
- Step 5. `Cockpit` (`src/view/cockpit.ts`): dashboard, canopy frame, struts and consoles
  around the camera, drawn after the world so nothing clips into it. Three screens show
  systems, power and radar from the same `HudState` the HUD reads; in cockpit view the HUD drops
  its own copies of those.
- Step 6. Graphics quality (`src/data/quality.ts`, Low / Medium / High in the pause menu,
  saved in settings) drives `Graphics` (`src/view/graphics.ts`): sun shadows around the player
  (mechs, structures and rocks cast; terrain receives), post-processing (FXAA, ACES tone
  mapping, light bloom, vignette), a glow layer on High, the panel normal map on mech
  materials, and the particle count. Mech materials carry a generated panel-and-grime texture
  and normal map (`src/view/surface.ts`). Particles (`src/view/particles.ts`): sparks on
  impacts, fire, sparks and smoke in explosions, dust on landing, exhaust from jets; one shared
  system per kind. The HUD is drawn by a second camera so screen effects leave it sharp.
- Step 7. `Sfx` rewritten: every world sound is placed relative to the camera (pan, distance
  gain, air absorption, speed-of-sound delay, more reverb with distance), with layered weapon,
  explosion, footstep (pitched by frame size) and landing sounds, servo whine while moving,
  two-layer jets and wind. Mix and placement numbers are in `src/data/audio.ts`.
- Step 8. Gamepad (`src/data/gamepad.ts`): standard-mapping pads drive the same `Intent`,
  their one-shot buttons run the same key handlers, and in menus the d-pad or stick moves focus,
  A chooses and B presses the screen's back button (`data-back`). The pause screen lists the
  layout.
- Step 9. HUD pass: backing panels behind the status, radio and info text; section integrity
  as coloured bars.

- Sign-off (2026-11-18). Traces on the 2019 16-inch MacBook Pro: Medium averaged 59.9 fps with a
  five-mech fight (median 16.7 ms, p99 17.7 ms, 0.4% of frames over 25 ms); High averaged 59.9
  fps with up to three mechs fighting (p99 17.7 ms, 0.3% slow, about 9.7 ms of game JavaScript
  and 5.2 ms of GPU time a frame in a fight). The remaining hitches are single frames of 23 to
  28 ms when mechs wake near a site, mostly their first render; left for the phase 8
  performance pass.

## Out of scope

Changing gameplay rules to suit assets. If a model does not fit a hit volume or hardpoint, adjust the model or its mapping.

## Key files and seams

- `PartVisual` in `src/view/parts/PartVisual.ts` and `MechVisual` in `src/view/mechVisual.ts`.
- `Effects` in `src/view/effects.ts`, `Sfx` in `src/view/audio.ts`.
- `PlayerInput.buildIntent` in `src/game/input.ts`.
- Hit volumes in `src/sim/hit.ts` stay analytic; models are matched to them, not the reverse.

## Verification

- E2E: a mech built from mixed procedural and imported parts loads, animates and fights; a missing asset falls back without errors.
- Screenshot comparison before and after for each visual change.
- Frame rate measured in a real browser after each addition.
- Every asset has an entry in the attribution file.

## Exit criteria

- The user is happy with how the game looks and sounds.
- Frame rate stays at or above the agreed target on their machine.
- All third-party assets are licensed for use and credited.
